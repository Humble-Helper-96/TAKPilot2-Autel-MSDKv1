# UI Theme / Style Consistency Review — 2026-08-03

Scope: the six pilot-facing screens and their layouts, the nine flight-screen custom views, and
`res/values/styles.xml`. Inherited Autel sample layouts are excluded (dead code, not pilot-reachable).

Each finding: **where** · **what** · **why a pilot cares** · **suggested fix** · **severity**.
Notes only — nothing was changed. Triage by number.

Target device is the **Autel Smart Controller, 1024×720dp landscape**. Verdicts assume that screen.

## Colour system

### 1. No colour tokens anywhere in the pilot UI — every colour is an inline literal
- **Where:** all pilot layouts + `styles.xml` + every custom view. `activity_tak_connect.xml`
  alone: 87 hex refs / 16 unique. Zero `@color/` references in any pilot layout.
- **What:** the same colours are re-typed as `#RRGGBB` in XML, in style definitions, and in
  Kotlin (`Color.parseColor`). There is no single source of truth.
- **Why it matters:** the app cannot be re-skinned or corrected consistently; a colour change
  means hunting literals across three file types, and drift is guaranteed (see #2, #3).
- **Fix:** add `res/values/takpilot_colors.xml` with named tokens (surface, card, accent,
  text-primary/secondary, state-go/caution/danger) and reference them everywhere.
- **Severity:** should-fix. Not visible to a pilot today, but it is the root cause of most
  findings below.

- **RESOLVED (declarative layer) 2026-08-03.** Created `res/values/takpilot_colors.xml` — semantic role-based tokens (surface/text-scale/accent/button/state). Migrated all 6 pilot layouts + `styles.xml` to `@color/tp_*`, value-preserving (verified on the flight screen: bg/shadow/accent/state values unchanged). The 5 near-duplicate greys were consolidated (#2). ⚠ Flight-HUD custom-view Kotlin colours NOT yet migrated — safety-tuned, need an on-device eyeball (see #3). Build green.
### 2. State colours have drifted into near-duplicates that a pilot must read as "the same"
- **Where:** greens `#2E7D32` (buttons, 8×), `#4CAF50` (accuracy-good, no-video notice,
  feed-joined, 3× in layouts), `#2E5C3A` (map-cache download), `#CCFFCC` (debug). Ambers `#FFB300`,
  `#FFC107`, `#FFCC00`, `#FFEB3B` all in use. Reds `#F44336`, `#FF3B30`, `#B71C1C`, `#EF5350`,
  `#5C2E2E`.
- **What:** "go/ok" is at least two greens, "caution" is four ambers, "danger/stop" is five reds —
  chosen ad hoc per file.
- **Why it matters:** on a flight screen, colour *is* the signal (battery band, accuracy ring,
  obstacle arc, RTH state). Four ambers that don't match teach a pilot that colour is decorative,
  which is the opposite of what a safety HUD needs.
- **Fix:** pick one triplet — one go-green, one caution-amber, one danger-red — as tokens, and
  map every current variant onto them. Note the accuracy ring (`#4CAF50/#FFEB3B/#F44336`) and the
  obstacle arc (`#FF3B30/#FFCC00`) use *different* green/amber/red than each other despite both
  being "how close is danger" cues.
- **Severity:** should-fix (borderline blocker for the flight-screen state colours).

- **PARTIALLY RESOLVED 2026-08-03.** Within-role grey near-dupes consolidated onto one token each (sub-perceptual shifts). The bright STATE colours (green/amber/red) live mostly in the flight-HUD custom views and were left as-is — consolidating those changes a safety display, so it needs an on-device check. Tokens are in place to make it a one-file change once the controller is available.
### 3. Flight-HUD colour is defined in three places at once
- **Where:** `activity_flight.xml` literals, `styles.xml` `hudText`, and the nine `*View.kt`
  files (`CrosshairView` 9 colours, `ObstacleEdgeView`, `BatteryGaugeView`, `ArOverlayView`,
  `LiveToggleView` 5 each).
- **What:** the single most safety-relevant screen has its colour source of truth split across
  XML, styles, and Kotlin.
- **Why it matters:** the accuracy ring, obstacle arcs and battery gauge should share one danger
  palette; today they can't be changed together.
- **Fix:** route the view colours through the same tokens (via `context.getColor(R.color.…)`).
- **Severity:** should-fix.

## Type scale

- **PARTIALLY RESOLVED 2026-08-03.** The XML + styles side is now tokenized. The Kotlin custom-view literals remain (deferred to on-device) — so the split is reduced from three places to one (the views).
### 4. Nine distinct text sizes, several one point apart
- **Where:** across home/flight/connect/debug: 11, 12, 13, 14, 15, 16, 18, 22, 26 sp.
- **What:** no type scale. 11/12/13/14/15/16 are visually indistinguishable pairs chosen per
  layout; `takLabelStyle` sets 13sp but layouts override with their own literals.
- **Why it matters:** inconsistent hierarchy makes the denser screens (Pre-Flight) harder to scan
  under time pressure.
- **Fix:** define a scale (e.g. caption 12 / body 14 / title 18 / display 22) as styles or dimens,
  and collapse the adjacent sizes onto it.
- **Severity:** polish.

## Buttons

### 5. Three different button-styling approaches coexist
- **Where:** inline `backgroundTint` (`activity_tak_connect.xml` 15×, `activity_takpilot2_home.xml`
  5×); style-driven (`takFovStepButton` sets its own tint); untinted default (flight screen).
- **What:** primary buttons are green `#2E7D32`, secondary are `#37474F`, destructive are
  `#B71C1C`/`#5C2E2E` — but this convention lives as repeated literals, not a set of button styles.
- **Why it matters:** the convention is actually good (green = go, grey = neutral, red =
  destructive) and worth making explicit so it can't be broken by the next button added.
- **Fix:** three button styles — `TakButton.Primary/.Neutral/.Destructive` — replacing the inline
  tints. Note the two destructive reds (`#B71C1C` home Quit vs `#5C2E2E` cache/deprovision) should
  become one.
- **Severity:** should-fix.

- **RESOLVED 2026-08-03.** Added `TakButton.Primary/.Neutral/.Info/.Confirm/.Danger/.DangerSoft` styles (colour role only; width/height stay per-button). Applied to all 27 buttons across the pilot layouts, removing the inline textColor+backgroundTint pairs. Log Out (a one-off grey) folded onto `.Neutral` to match its sibling buttons (shade shift #555555→#37474F, intended). Build green.
### 6. `STOP / QUIT` and `Pre-Flight Setup` are the same visual weight as `Field Guide`/`Debug Log`
- **Where:** `activity_takpilot2_home.xml:78-117` — five stacked full-width buttons.
- **What:** the destructive Quit and the primary Pre-Flight sit in the same button stack as
  routine navigation, differentiated only by tint.
- **Why it matters:** a pilot in a hurry can tap Quit thinking it's a menu item. It is the most
  consequential control on the screen.
- **Fix:** separate Quit visually (own row, or move it), and confirm its tap opens the existing
  confirm dialog (it does — `TakPilotHomeActivity:123`).
- **Severity:** polish.

## Layout / density for the real screen

- **RESOLVED 2026-08-03.** STOP / QUIT moved to the BOTTOM of the Quick Controls card, separated from the four navigation/setup buttons by a divider and a 16dp gap. Id unchanged, so its confirm dialog still fires. A hurried pilot can no longer hit it mistaking it for a menu row.
### 7. Only the flight screen uses `@dimen/`; home and Pre-Flight use raw dp literals
- **Where:** `activity_flight.xml` uses `@dimen/flight_map_size` etc. (defaults exist in
  `values/dimens.xml`: 130dp, with `values-w820dp` 180dp and `values-h440dp` 160dp overrides).
  `activity_takpilot2_home.xml` and `activity_tak_connect.xml` use 0 `@dimen/`.
- **What:** only the map column adapts to screen size; everything else is fixed dp.
- **Why it matters:** the 1024×720dp controller is wider and shorter than a phone. Pre-Flight is a
  1021-line single-column form that was tuned on a phone aspect ratio; the home screen already
  carries a scar comment about clipping the last card (`activity_takpilot2_home.xml:126-134`).
- **Fix:** there is **no `sw600dp`/`sw720dp` smallestWidth bucket targeting the controller** — add
  one and confirm Pre-Flight and Home on the real 1024×720 viewport. This is best done with the
  device connected (screenshots).
- **Severity:** should-fix — needs on-device confirmation, which yesterday's session never did for
  Pre-Flight at controller size.

### 8. Flight-screen pill buttons are 46×34dp — below the 48dp touch-target guideline
- **Where:** `activity_flight.xml` — AR/photo/zoom/IR/lights pills all `46dp × 34dp`; TAK/back/RTH
  `34-40dp × 34dp`; map zoom `48×32`.
- **What:** the height (34dp) is well under the 48dp minimum, and a pilot is often flying while
  reaching for these.
- **Why it matters:** small targets on a moving aircraft mean missed taps at the worst time. The
  drop-pin button is correctly oversized (56×46) for exactly this reason — the rest are not.
- **Fix:** raise the pill height toward 44-48dp, budget permitting; at minimum confirm the hit
  rects on the real controller. The comment at `:173-175` shows the sizing was deliberately copied
  from DJI — verify DJI's target device matched this one (the memory note says RT3 verdicts don't
  transfer).
- **Severity:** should-fix.

## Styles / theme hygiene

### 9. `styles.xml` named styles hardcode hex instead of referencing tokens
- **Where:** `takFieldStyle` (`#FFFFFF`/`#2A2A2A`/`#666666`), `takColumnRadio`/`takArCheck`
  (`#9AC4FF`), `homeCard*`, `TakDialogTheme`, `hudText` — all literal.
- **What:** even the centralised styles aren't a single source of colour truth.
- **Why it matters:** fixing #1 must include the styles, or half the colours stay orphaned.
- **Fix:** fold into the token set from #1.
- **Severity:** should-fix (part of #1).

- **RESOLVED 2026-08-03.** All `tak*`/`home*`/`hudText`/`TakDialogTheme` styles now reference `@color/tp_*`. Part of #1.
### 10. Low style reuse — most `tak*` styles are used in exactly one layout
- **Where:** `takLabelStyle`, `takFieldStyle`, `homeCardValue`, `hudText`, `takFovStepButton`,
  `takFovValue`, `takArCheck` — one layout each.
- **What:** styles exist but the second screen that needed the same treatment re-typed literals
  instead of reusing them.
- **Why it matters:** the pattern that produced #1–#5 will keep producing them.
- **Fix:** when fixing the above, prefer extending existing styles over new literals.
- **Severity:** polish.

### 11. `TakDialogTheme` is applied programmatically, never from a layout — and the two AR dialogs bypass it
- **Where:** `TakDialogTheme`/`.Destructive` applied in code (TakConnectActivity, FlightActivity,
  etc.); `dialog_ar_options.xml`/`dialog_ar_fov.xml` are inflated by the Activity's own inflater
  with hardcoded colours (`dialog_ar_options.xml:9-10` comment admits it).
- **What:** most dialogs get the dark TAK theme; the two AR dialogs are styled independently.
- **Why it matters:** the AR dialogs are the one place the menu "didn't look like the rest of it"
  (the comment says this was already fixed once for the multi-choice list).
- **Fix:** verify the two AR dialogs match `TakDialogTheme` on the real screen; unify the
  background/accent literals onto the tokens.
- **Severity:** polish.
