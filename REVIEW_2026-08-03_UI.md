# User-interface review: theme and style — 3 August 2026

**Written in Simplified Technical English (ASD-STE100).**

> **This is a record of one date.** Section 6 gives the result of each finding after a check on the
> real controller. The user interface is satisfactory on the device. Do not read this document as a
> list of open work.

**Scope:** the six screens that a pilot uses, their layouts, the nine custom views on the flight
screen, and `res/values/styles.xml`. The layouts from the Autel sample are not in the scope. A pilot
cannot reach them.

**The target device is the Autel Smart Controller, 1024 x 720 dp, landscape.** Each result applies
to that screen.

## 1. Colours

### Finding 1: no colour tokens (severity: should fix)

**Where:** all the pilot layouts, `styles.xml` and each custom view. The file
`activity_tak_connect.xml` alone had 87 colour values, of which 16 were different. No pilot layout
used a `@color/` reference.

**What:** The same colours were written again as `#RRGGBB` in the XML, in the styles and in the
Kotlin code (`Color.parseColor`). There was no single source.

**Why it is important:** A person cannot change the appearance of the application in a consistent
manner. To change one colour, a person must find the values in three types of file. A difference is
then certain. Findings 2, 3, 5 and 9 all come from this.

**Result: CLOSED for the declarative layer.** `res/values/takpilot_colors.xml` was created with
tokens that give a role: surface, text scale, accent, button and state. All six pilot layouts and
`styles.xml` now use `@color/tp_*`. The values did not change. The five greys that were almost the
same were made into one (finding 2). The colours in the Kotlin custom views were not changed. Read
finding 3.

### Finding 2: the state colours are almost the same as each other (severity: should fix)

**Where:** The greens were `#2E7D32`, `#4CAF50`, `#2E5C3A` and `#CCFFCC`. The ambers were `#FFB300`,
`#FFC107`, `#FFCC00` and `#FFEB3B`. The reds were `#F44336`, `#FF3B30`, `#B71C1C`, `#EF5350` and
`#5C2E2E`.

**What:** "Go" was a minimum of two greens. "Caution" was four ambers. "Danger" was five reds. A
person selected each one for one file.

**Why it is important:** On a flight screen the colour IS the signal. It gives the battery band, the
accuracy ring, the obstacle arc and the RTH state. Four ambers that do not agree teach a pilot that
the colour is decoration. A safety display needs the opposite.

The accuracy ring and the obstacle arc used different greens, ambers and reds from each other. Both
show how near the danger is.

**Result: PART CLOSED.** The greys that were almost the same are now one token each. The bright
state colours are in the flight-HUD custom views. They were not changed. Read section 6.

### Finding 3: the flight-HUD colours are in three places (severity: should fix)

**Where:** The literal values in `activity_flight.xml`, the `hudText` style in `styles.xml`, and the
nine `*View.kt` files.

**What:** The most safety-relevant screen has its colours in the XML, in the styles and in the Kotlin
code.

**Why it is important:** The accuracy ring, the obstacle arcs and the battery gauge must use one set
of danger colours. Today a person cannot change them together.

**Result: PART CLOSED.** The XML and the styles now use tokens. The Kotlin values stay. Therefore the
colours are in one place, not three. Read section 6 for the decision.

## 2. Text sizes

### Finding 4: nine different text sizes (severity: polish)

**Where:** The home screen, the flight screen, the connect screen and the debug screen use 11, 12,
13, 14, 15, 16, 18, 22 and 26 sp.

**What:** There is no scale. The sizes 11, 12, 13, 14, 15 and 16 are pairs that a person cannot see a
difference between. The `takLabelStyle` sets 13 sp, but the layouts write their own values.

**Why it is important:** A hierarchy that is not consistent makes the more dense screens difficult to
read quickly.

**Correction:** Make a scale, for example caption 12, body 14, title 18 and display 22.

## 3. Buttons

### Finding 5: three methods to make a button (severity: should fix)

**Where:** `backgroundTint` in the layout (15 times in one file, 5 times in another), a style that
sets its own tint, and the default with no tint.

**What:** The primary buttons are green, the secondary buttons are grey and the destructive buttons
are red. This convention is repeated values. It is not a set of styles.

**Why it is important:** The convention is good. Green is go, grey is neutral and red is destructive.
Make it explicit. The next button that a person adds cannot then break it.

**Result: CLOSED.** The styles `TakButton.Primary`, `.Neutral`, `.Info`, `.Confirm`, `.Danger` and
`.DangerSoft` were added. They set the colour role only. The width and the height stay with each
button. All 27 buttons in the pilot layouts use them.

### Finding 6: the Quit button has the same weight as the navigation buttons (severity: polish)

**Where:** `activity_takpilot2_home.xml`, five buttons of full width in one stack.

**What:** The destructive Quit button and the primary Pre-Flight button are in the same stack as the
usual navigation buttons. Only the colour is different.

**Why it is important:** A pilot who is in a hurry can touch Quit and think that it is a menu item.
It is the control with the largest consequence on that screen.

**Result: CLOSED.** STOP / QUIT moved to the bottom of the Quick Controls card. A divider and a 16 dp
space separate it from the four other buttons. Its identifier did not change, so its confirmation
dialog still operates.

## 4. Layout for the real screen

### Finding 7: only the flight screen uses `@dimen/` (severity: should fix)

**Where:** `activity_flight.xml` uses `@dimen/flight_map_size`. The home screen and the connect
screen use no `@dimen/` values.

**What:** Only the map column changes with the size of the screen. The other items have fixed values.

**Why it is important:** The 1024 x 720 dp controller is wider and shorter than a telephone. The
Pre-Flight screen is a long form in one column that a person made for a telephone shape.

**Result: NO CHANGE NECESSARY.** Read section 6.

### Finding 8: the flight-screen buttons are 46 x 34 dp (severity: should fix)

**Where:** `activity_flight.xml`. The AR, photo, zoom, IR and lights buttons are 46 dp x 34 dp.

**What:** The height of 34 dp is much less than the guideline minimum of 48 dp. A pilot frequently
touches these buttons during a flight.

**Why it is important:** A small target on a moving aircraft gives a missed touch at the worst time.
The drop-marker button is correctly larger (56 x 46).

**Result: NO CHANGE NECESSARY.** Read section 6.

## 5. Styles

### Finding 9: the styles contain literal colours (severity: should fix)

**Where:** `takFieldStyle`, `takColumnRadio`, `takArCheck`, the home card styles, `TakDialogTheme`
and `hudText`.

**What:** Even the central styles were not one source of colour.

**Result: CLOSED.** All these styles now use `@color/tp_*`. This was part of finding 1.

### Finding 10: the styles have little re-use (severity: polish)

**Where:** `takLabelStyle`, `takFieldStyle`, `homeCardValue`, `hudText`, `takFovStepButton`,
`takFovValue` and `takArCheck`. Each one is in one layout.

**What:** The styles exist, but the second screen that needed the same appearance wrote the values
again.

**Why it is important:** The behaviour that made findings 1 to 5 will continue to make more of them.

**Correction:** Extend an existing style. Do not write new values.

### Finding 11: the two AR dialogs do not use `TakDialogTheme` (severity: polish)

**Where:** The activity applies `TakDialogTheme` in the code. The two AR dialog layouts are inflated
by the inflater of the activity and have literal colours.

**Result: NO CHANGE NECESSARY.** Read section 6.

## 6. Check on the device, 3 August 2026

The check used the Autel Smart Controller with the aircraft connected. The flight screen was reached
correctly, from the Home screen. The live video, the telemetry and the obstacle radar all operated.

- **Finding 11, the AR dialogs: CORRECT, no change.** The AR dialog uses the dark TAK theme with
  blue checkboxes and radio buttons. It agrees with the other screens. The concern in the review was
  about the older list, which was already replaced.
- **Finding 7, the density: CORRECT, no change.** The Home screen, the Pre-Flight screen and the
  flight screen all use the 1024 x 720 screen well. Nothing is cut. There is no wasted space.
- **Finding 8, the touch targets: SATISFACTORY, no change.** The 46 x 34 dp buttons are easy to read
  and easy to touch on the physical screen. The drop-marker button is correctly larger. The raw
  numbers suggested a problem that does not exist on this device.
- **Finding 4, the text sizes: SATISFACTORY.** The HUD text hierarchy is easy to read during a
  flight. A tidy of the scale is desirable but is not necessary.
- **Findings 2 and 3, the flight-HUD colours: CORRECT on the device. NOT changed.** The green, amber
  and red safety colours all operate correctly. The obstacle arcs become red when an object is near
  (3.8 ft and 1.6 ft at the rear). The accuracy ring warns when the gimbal is level. The battery
  gauge and the RTH value are correct. The reds and the ambers that are almost the same cannot be
  told apart in use.

  **Decision: keep the colours in the HUD custom views as literal values.** A change to tokens gives
  no difference that a user can see. It touches the `onDraw` code of a safety display. A person
  cannot check the full change without control of the gimbal and the obstacles during a flight.
  Therefore it is not correct to change safety code that operates. The tokens
  (`tp_state_go`, `tp_state_caution`, `tp_state_danger`) exist if a future flight session decides to
  do this.

## 7. Other observations

- **The accent blue `#9AC4FF`** is used correctly for each interactive item. Keep it as the accent
  token.
- **There is no `values-night` directory.** This is correct for a flight application. Do not add a
  light theme.
- **The home screen layout has comments that record earlier failures.** Read them before you change
  that screen. They record real problems where content was cut at specific sizes.

## 8. Summary

The user interface is satisfactory on the real device.

Most of the items that were left were theoretical. When a person saw them on the device, they did not
need a change.

The two items that remain are the text scale (finding 4) and the colour tokens in the HUD (finding
3). Both are improvements to maintenance. Neither stops a release.
